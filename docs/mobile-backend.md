# Mobile backend B — phase 2

[README](../README.md) | [Architecture](../ARCHITECTURE.md) | [Verification](TEST-MATRIX.md#current-verification-status) | [Deployment](deployment.md) | [Mobile flows](flows/README.md#mobile-flows)

This example supports both its existing browser SPA and native Mobile A. Mobile can run alone (EXAMPLE_MODE=mobile) or alongside browser (both), with separate credentials, routes and session stores. No Mobile A, Rita ID or Portal source changes are required by this implementation.

The client contract is recorded in the sibling [Mobile A contract](../../oauth02-mobile-integration-example/docs/mobile-backend-contract.md). That phase-1 document predates this implementation; the endpoints below now exist in B when enabled. Its statement that B is not implemented is historical. The executable compatibility check uses the actual A adapter without copying it or importing it into B's build.

## Configuration

Use [.mobile.env.example](../.mobile.env.example) to create .mobile.env only if it does not already exist, then run npm run dev:mobile (or npm run start:mobile after building). Mobile-only requires no browser credentials, portal origin or browser callback. Register a Rita **public** mobile client, with `authorization_code` and `refresh_token`, scopes `openid profile email`, callback `rita-id-app://redirect`. The public client must already be provisioned; this change does not provision clients or modify the portal UI/database.

| Setting | Default / rule |
| --- | --- |
| EXAMPLE_MODE | mobile for the isolated profile; both for a combined legacy-command process. |
| RITA_MOBILE_CLIENT_ID | Required in mobile/both, must differ from browser client ID in both; never a browser-provided arbitrary client. |
| MOBILE_SESSION_MAX_AGE_HOURS | 8; greater than 0, at most 24. Absolute, not extended by OAuth refresh. |
| MOBILE_MAX_SESSION_ENTRIES | 1000; positive safe integer. Counts reservations and established mobile sessions. |
| MOBILE_MAX_HANDOFF_ENTRIES | 2000; positive safe integer. Counts pending, replay and tombstone records. |
| HOST | 127.0.0.1; bind hostname/IP. May be set to a device-reachable interface, e.g. 0.0.0.0 for a controlled local test. |

Mobile uses the same RITA_API_URL/JWKS as browser, but all refresh/revoke calls use RITA_MOBILE_CLIENT_ID **without client_secret**. Browser retains its confidential client. HOST does not rewrite APP_BASE_URL, cookies, callback URLs, TLS or trust-proxy settings. Web/both retain loopback reverse-proxy trust for HTTPS browser configuration; mobile-only does not enable trust proxy.

Set A's EXPO_PUBLIC_APP_BACKEND_BASE_URL to the mobile process's device-reachable **origin**, e.g. http://<computer-LAN-IP>:3004, without `/api`. HTTP is only for A development; release A requires HTTPS. A physical phone's localhost is itself. This is still a one-process RAM demo: NODE_ENV=production is rejected, restart loses both stores and replay state, and multiple workers are unsupported. No .env is automatically edited.

Legacy npm run dev / npm start still read .env; MOBILE_AUTH_ENABLED=true selects both only when EXAMPLE_MODE is absent.
Both requires browser credentials as well as the separate public mobile ID. Explicit profiles do not read .env.
See [profile commands, precedence and simultaneous processes](../README.md#separate-mobile-process-and-legacy-startup).

## HTTP contract

All mobile routes are under `/api/mobile`, before browser cookies, CSRF, Origin checks and the 4 KB browser parser. Mobile has a separate JSON parser with a 16 KB limit and error boundary. Responses are no-store, never set/clear cookies, and never fall back to the SPA. Mobile rejects an Origin header; browser CORS is not enabled. Unknown method/path returns JSON 404 even with malformed body.

| Method/path | Input | Success |
| --- | --- | --- |
| POST /api/mobile/auth/session | JSON: handoffId, clientId, accessToken, refreshToken, no extra fields | 200: sessionKey, expiresAt, profile |
| GET /api/mobile/me | Authorization: Bearer X | 200: profile, expiresAt |
| POST /api/mobile/auth/logout | Authorization: Bearer X; no body | 200: loggedOut=true, revokeConfirmed boolean |
| GET /api/mobile/private/example | Authorization: Bearer X | 200: message, subject |

The 64-character lowercase-hex handoffId is generated by A once. Tokens and clientId must be nonempty strings without whitespace. X is 32 random bytes, base64url (43 characters), indexed by SHA-256. Missing, malformed, duplicate or unknown Authorization headers cannot authenticate. Cookies never authenticate mobile, and putting X in the browser cookie cannot authenticate browser.

`expiresAt` is a UTC ISO timestamp of **B's absolute session deadline**, not access-token expiration. `profile` is the existing browser profile contract: sub (Rita UUID), name, email, employee_id, phone_number, is_developer, groups, avatar and position. Nullable fields and the complete nested position parser remain unchanged. No OAuth token, CSRF, secret or internal refresh counters are included. No local account database or additional business-role system is introduced: these demonstration resources permit the validated OAuth identities accepted by the shared profile contract, excluding DEVELOPER.

Errors use `{ "error": "machine_code" }`: 400 invalid_body; 401 not_authenticated; 403 forbidden/invalid_origin; 409 handoff_conflict; 413 body_too_large; 502 integration_error; 503 temporarily_unavailable/store_full with Retry-After. Raw provider errors and credentials are never included. Invalid content type is 400. Mobile logout returns 401 for a missing/expired/invalid X, which A handles as local sign-out.

## Handoff validation and accepted limit

B verifies the original JWT signature with RS256/JWKS, kid, subject, audience, expiry and token_use=oauth_access, then verifies profile/subject through userinfo. Required original scopes include openid/profile/email. Invalid access proof does not trigger refresh.

B refreshes the submitted refresh token once using the public mobile client. It retains the replacement immediately, then verifies the new JWT and userinfo against the **same subject, client and scope set** (including the returned refresh response's scope). Only then does it create X. Rejected replacement credentials are revoked best-effort.

Rita ID access tokens currently do not contain an OAuth session ID, so this proves identity/client/scope consistency, **not that the original tokens were issued together or belong to the same original grant**. Two grants for the same subject/client/scopes cannot be distinguished here. This is the explicitly accepted phase-2 boundary; no full OIDC or token-pair-binding claim is made. B's rotation does not immediately revoke the original access JWT; A must discard its OAuth tokens after handoff.

## Idempotency and uncertain failures

The [handoff flow](flows/mobile-flows/01-login-and-handoff.md) records capacity reservation, payload binding, concurrent requests, replay and uncertain provider responses. Contract guarantees are identical replay for a matching payload, 409 on conflicting binding, a 150-second replay window from success, and no replay of revoked sessions. A's 120-second retry window does not extend B's session deadline. Ambiguous token rotation is terminal; known replacement credentials can recover through verification-only retry.

## Established session and browser isolation

The [private request flow](flows/mobile-flows/02-private-resource-request.md) and [termination flow](flows/mobile-flows/03-refresh-and-session-termination.md) describe verification, rotation and logout. X and its absolute deadline remain stable across refresh. Browser cookies/CSRF and mobile Bearer sessions use separate stores/adapters. No mobile manual refresh endpoint is exposed, and logout reports local deletion separately from confirmed upstream revocation.

## Validation and live acceptance

```powershell
npm run lint
npm run typecheck
npm test
npm run build
npm run test:browser
npm run test:mobile-compat
npm run docs:check
git diff --check
```

The compatibility command requires sibling `../oauth02-mobile-integration-example`; use MOBILE_EXAMPLE_PATH to choose another checkout. It is explicitly separate from standard tests/build and imports only A's HTTP adapter. It runs against local B and a fictional RSA/JWKS provider, without .env, accounts or databases. It checks handoff/replay, A's profile parsing, private access, B refresh and logout. It is not a native-device or live-provider test.

After provisioning fictional clients/accounts in a suitable environment, manually test native login/consent/callback, handoff, restart A, access expiry/B refresh, logout, another account, lost handoff response, offline foreground, B restart and permission denial. Separately validate TLS/reverse-proxy and the browser flow on its registered origin. These checks are not implied by unit tests or Chrome running against a fake provider.
